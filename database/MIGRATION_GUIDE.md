# Database Schema Alignment Migration Guide

**Migration ID:** telemetry_alignment_20261007
**Status:** Ready for Execution
**Impact:** HIGH - Recreates telemetry_logs table with new schema

---

## Overview

This migration aligns the Supabase database schema with the complete telemetry payload from the ESP32 receiver firmware. The new schema uses shorter field names (`volts`, `amps`, `watts`, `speed_h`, `speed_g`) matching the receiver JSON output, and adds support for pit-to-driver commands and race flags.

---

## Schema Changes

### 1. telemetry_logs Table

**Before (UUID-based):**
```sql
CREATE TABLE public.telemetry_logs (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    session_id TEXT NOT NULL,
    packet_id BIGINT NOT NULL,
    current NUMERIC(8,2) NOT NULL,
    voltage NUMERIC(8,2) DEFAULT 0.00,
    power NUMERIC(8,2) DEFAULT 0.00,
    speed_hall NUMERIC(8,2) DEFAULT 0.00,
    speed_gps NUMERIC(8,2) DEFAULT 0.00,
    latitude NUMERIC(10,6) DEFAULT 0.00,
    longitude NUMERIC(10,6) DEFAULT 0.00,
    rssi NUMERIC(6,2),
    snr NUMERIC(5,2),
    created_at TIMESTAMPTZ DEFAULT NOW()
);
```

**After (BIGINT-based, short field names):**
```sql
CREATE TABLE public.telemetry_logs (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    session_id TEXT DEFAULT 'race-session-48v',
    packet_id BIGINT,
    volts NUMERIC(5,2),
    amps NUMERIC(5,2),
    watts NUMERIC(6,2),
    speed_h NUMERIC(4,1),
    speed_g NUMERIC(4,1),
    rssi INT,
    snr NUMERIC(4,1)
);
```

**Key Changes:**
- ✅ `id` changed from UUID to BIGINT GENERATED BY DEFAULT AS IDENTITY
- ✅ Field names shortened: `current` → `amps`, `voltage` → `volts`, `power` → `watts`, `speed_hall` → `speed_h`, `speed_gps` → `speed_g`
- ✅ Removed `latitude` and `longitude` (not used in current implementation)
- ✅ Added default session_id: `'race-session-48v'`
- ✅ Changed precision: `NUMERIC(8,2)` → `NUMERIC(5,2)` for volts/amps (sufficient for 48V system)
- ✅ Changed `rssi` from NUMERIC to INT (integer dBm values)

### 2. commands Table (NEW)

```sql
CREATE TABLE public.commands (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    session_id TEXT,
    command_name TEXT,
    status TEXT DEFAULT 'PENDING',
    acknowledged_at TIMESTAMPTZ
);
```

**Purpose:** Track pit-to-driver commands with acknowledgment timestamps.

### 3. race_flags Table (NEW)

```sql
CREATE TABLE public.race_flags (
    id INT PRIMARY KEY DEFAULT 1,
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    active_flag TEXT DEFAULT 'GREEN'
);
```

**Purpose:** Single-row table for race control flag state (GREEN, YELLOW, RED, BLACK).

## Execution Steps

### Step 1: Backup Existing Data

The migration script automatically creates a backup table:
```sql
CREATE TABLE IF NOT EXISTS public.telemetry_logs_backup_20261007 AS
SELECT * FROM public.telemetry_logs;
```

**Manual Backup (Recommended):**
```sql
-- Export to CSV
COPY public.telemetry_logs TO 'telemetry_logs_backup_20261007.csv' CSV HEADER;
```

### Step 2: Run Migration

**Option A: Supabase Dashboard (Recommended)**
1. Go to https://app.supabase.com
2. Navigate to your project
3. Go to SQL Editor
4. Open `database/migration_telemetry_alignment.sql`
5. Click **Run** or press `Ctrl+Enter`

**Option B: Supabase CLI**
```bash
supabase db push --database-url="postgresql://postgres:[YOUR-PASSWORD]@db.[YOUR-PROJECT-REF].supabase.co:5432/postgres"
```

**Option C: psql CLI**
```bash
psql -h db.[YOUR-PROJECT-REF].supabase.co -U postgres -d postgres -f database/migration_telemetry_alignment.sql
```

### Step 3: Verify Migration

**Check Table Schemas:**
```sql
\d public.telemetry_logs
\d public.commands
\d public.race_flags
```

**Check Realtime Publication:**
```sql
SELECT * FROM pg_publication_tables WHERE pubname = 'supabase_realtime';
```

Expected output:
```
pubname        | schemaname | tablename
---------------+------------+------------
supabase_realtime | public     | telemetry_logs
supabase_realtime | public     | commands
supabase_realtime | public     | race_flags
```

**Check RLS Policies:**
```sql
SELECT tablename, policyname, permissive, roles, cmd
FROM pg_policies
WHERE schemaname = 'public'
ORDER BY tablename, policyname;
```

### Step 4: Test Data Insertion

1. Go to Database → Replication

## Rollback Plan

If migration fails or causes issues:

### Option 1: Restore from Backup Table
```sql
-- Drop new table
DROP TABLE public.telemetry_logs CASCADE;

-- Recreate from backup
CREATE TABLE public.telemetry_logs AS
SELECT * FROM public.telemetry_logs_backup_20261007;

-- Add back indexes
CREATE INDEX idx_telemetry_logs_session_id ON public.telemetry_logs(session_id);
CREATE INDEX idx_telemetry_logs_created_at ON public.telemetry_logs(created_at DESC);

-- Re-enable RLS
ALTER TABLE public.telemetry_logs ENABLE ROW LEVEL SECURITY;

-- Re-add policies
CREATE POLICY "public_allow_anon_read" ON public.telemetry_logs
FOR SELECT TO anon USING (true);

CREATE POLICY "public_allow_anon_insert" ON public.telemetry_logs
FOR INSERT TO anon WITH CHECK (true);

-- Re-enable Realtime
ALTER PUBLICATION supabase_realtime ADD TABLE public.telemetry_logs;
```

### Option 2: Restore from CSV Backup
```sql
-- Drop new table
DROP TABLE public.telemetry_logs CASCADE;

-- Recreate old schema
-- (Run original schema.sql lines 92-106)

-- Import from CSV
COPY public.telemetry_logs FROM 'telemetry_logs_backup_20261007.csv' CSV HEADER;
```

## Troubleshooting

### Issue: Migration fails with "relation already exists"
**Solution:** The migration script includes `DROP TABLE IF EXISTS` statements. Ensure you're running the complete script, not partial statements.

### Issue: Realtime subscription not working
**Solution:** Verify publication:
```sql
SELECT * FROM pg_publication_tables WHERE pubname = 'supabase_realtime';
```
If tables are missing, manually add them:
```sql
ALTER PUBLICATION supabase_realtime ADD TABLE public.telemetry_logs;
ALTER PUBLICATION supabase_realtime ADD TABLE public.commands;
ALTER PUBLICATION supabase_realtime ADD TABLE public.race_flags;
```

### Issue: Gateway script gets 400 error from Supabase
**Solution:** The script has fallback logic that will handle schema mismatches. Check console for "SUPABASE SCHEMA NOTICE" messages and ensure migration was completed.

### Issue: Dashboard shows no telemetry after migration
**Solution:**
1. Check browser console for errors
2. Verify Supabase URL and anon key in `.env`
3. Check Realtime publication status
4. Insert test record via SQL Editor
5. Verify Realtime updates in Supabase Dashboard
